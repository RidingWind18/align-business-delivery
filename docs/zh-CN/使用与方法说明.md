# 使用与方法说明

`align-business-delivery` 是面向存量业务系统和复杂业务功能的交付对齐 Skill。它帮助 AI 识别当前有效的业务事实、原型、契约、代码、任务边界和验证证据，减少范围扩大、旧口径复活、页面偏离和长任务中断后的混乱。

## 什么时候使用

- 需求描述还比较模糊，需要先形成可复核的业务基线。
- PRD、原型、代码和数据库之间存在差异。
- 一个功能跨多个模块、客户端、仓库或开发人员。
- 长任务中断、派生或多轮纠偏后，当前范围容易丢失。
- 项目没有文档，或者旧文档很多但不知道哪些仍然有效。
- 开发完成后，需要区分代码完成、技术验证、真实运行和业务验收。

普通文案、小样式和局部修复不需要机械运行完整流程。Skill 会按业务风险选择轻量闭环、标准模块或完整设计。

## 它会做什么

1. 核对可以从代码、文档、原型、数据库和历史中查证的事实。
2. 区分用户确认、代码事实、推导结论、建议、待确认和明确排除项。
3. 判断当前任务允许修改什么，哪些相邻问题只记录而不实施。
4. 需要页面实现时消费当前原型，同时遵循现有项目组件和编码规范。
5. 多模块协作时识别依赖、所有权、共享契约和真实完成状态。
6. 交付时对照目标、实际改动、验证证据和残余风险。

它不替代产品设计、技术方案、TDD、调试、代码审查、浏览器测试、Git 工作流或项目管理工具；这些工作仍由 AI 工具本身或对应专业能力完成。

## Skill 文件职责

安装目录采用“一个入口、按需读取”的结构。`SKILL.md` 是唯一入口和路由规则，`references/` 中的文件不是需要分别安装或手工调用的独立 Skills。正常使用时只需调用 `align-business-delivery`，AI 应根据当前问题读取相关 reference，而不是一次加载全部文件。

| 文件 | 主要职责 | 通常何时使用 |
| --- | --- | --- |
| `SKILL.md` | 定义 Skill 的定位、轻量/标准/完整模式、强制门禁、reference 路由、专业能力交接和完成收口 | 每次 Skill 生效时首先读取 |
| `agents/openai.yaml` | 提供 Codex 界面展示名称、简短说明和默认调用提示；不承载业务规则 | Codex 发现和展示 Skill 时使用 |
| `references/requirement-intake-and-convergence.md` | 把模糊需求、零散条目和连续反馈整理为可复核基线，并区分已确认事实、代码事实、推导、建议、待确认和排除项 | 初始需求模糊、逐项确认、多轮纠偏、引用历史回复或恢复父任务时 |
| `references/source-arbitration-and-baseline.md` | 按业务目标、页面交互、代码现状、项目规范和当前任务等不同维度裁决冲突来源，要求可查事实先核验 | PRD、原型、代码、数据库、历史记录或当前口径互相不一致时 |
| `references/prototype-and-product-flow.md` | 确定原型投入程度，约束原型到真实页面的消费证据，保护入口、筛选、表格、操作、弹窗、数据流和未改区域 | 制作原型、按原型开发页面、核对页面偏差或决定是否需要重画原型时 |
| `references/document-and-artifact-lifecycle.md` | 管理当前依据、历史材料、阶段文档、SQL、测试和交接产物的消费者、有效期、提交与收口边界 | 文档可能过期、过程材料是否提交、初始化与迁移资产容易混淆时 |
| `references/documentation-baseline-diagnosis.md` | 诊断项目现有文档是否够用，并根据真实消费者和风险推荐兼容现状的最小文档体系 | 新项目缺少文档、旧项目文档失修，或用户不知道应维护哪些文档时 |
| `references/business-model-state-and-refactor.md` | 在核心对象、关系、粒度、状态和流程重构中保护原有业务语义，识别迁移、兼容和追溯要求 | 改表、改状态机、改绑定关系、改最终结果来源或重构既有流程时 |
| `references/module-delivery-and-coordination.md` | 定义模块交付包、READY/BLOCKED 等业务状态、前置依赖、共享契约、所有权和失效传播 | 多模块、多端、多仓库或多人并行，需要判断哪些可先行开发时 |
| `references/execution-scope-guard.md` | 固定当前写入范围和交付批次，处理相邻发现、中断恢复、共享消费者、危险动作及重复修复熔断 | 开始写文件、任务中断恢复、发现额外问题、修改共享能力或范围可能扩大时 |
| `references/delivery-convergence-and-evidence.md` | 对照目标、实际改动和证据，区分编码、自动验证、运行验证、用户验收及整体完成 | 阶段收口、提交推送、正式交接、复杂批次中点或声明完成前 |

这些文件按问题组合使用，不代表固定瀑布阶段。例如一个局部页面修复可能只需要入口规则、原型消费和执行范围；跨仓库状态重构则可能同时需要来源裁决、业务模型、模块协作和交付证据。专业 Skill 仍负责产品设计、编码、调试、测试或代码审查，`align-business-delivery` 只向其提供当前有效的业务基线和边界。

## 文档基线诊断

当用户不知道项目应该维护哪些文档，或项目文档缺失、老旧、重复和互相冲突时，Skill 会先分析：

- 项目规模、阶段、模块和仓库关系；
- 文档实际消费者和维护人员；
- 现有 README、协作说明、设计、原型、接口、数据、任务和验证材料；
- 哪些材料当前有效、仅供历史追溯、尚待确认或只存在本机；
- 哪些变化会影响其他模块或让既有验收失效。

然后给出最小建议：哪些保留、修复、合并、归档、创建或暂时不需要。只有用户要求或授权后才落地文件，不会因为触发 Skill 就给每个项目生成固定编号的整套文档。

用户已有的文档体系、命名方式和维护想法优先作为约束。只要现有体系能够回答实际交付问题，Skill 就应沿用它；发现风险时先说明影响对象和失败方式，再提出兼容现有体系的最小调整。未经同意，不会重命名、移动、拆分、合并、归档或替换用户文档。

判断一份文档是否值得维护，主要看三个问题：

```text
谁使用它？
它决定什么？
什么变化发生时必须更新它？
```

## 最小调用示例

```text
$align-business-delivery

这个旧项目文档比较乱。请先结合当前代码和现有文档，判断哪些仍然有效，推荐一套适合当前项目的最小文档体系；先给建议，不要直接批量创建文件。
```

也可以使用自然语言描述任务。是否能被自动发现取决于所使用工具的 Skill 支持方式。

## 为什么正式规则仍使用英文

当前 `SKILL.md` 和 references 是 AI 执行真源，现有回归证据基于这套英文规则。英文不是天然比中文更准确；暂时保留英文是为了避免未经验证的整套翻译改变规则语义。

人类使用入口、UI 名称和本说明优先使用中文。后续若进行中英文同场景对照并确认没有能力退化，可以再调整执行真源语言。仓库不会长期维护两套内容相同的完整 Skill，以免规则分叉。

## 当前边界

- Skill 建议的是与可靠业务交付有关的最小文档体系，不建设通用企业 Wiki。
- 不把某个项目的文档编号、业务表名或人员分工写成通用规则。
- 不要求用户放弃自己的文档体系，也不把 Skill 的角色分类强制映射为固定文件。
- 不因“以后可能需要”提前创建无消费者的文档。
- 历史材料不会仅因过时而自动删除；应先明确当前替代依据和历史用途。
